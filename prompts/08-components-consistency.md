# 08 — Components & Consistency

**Use when:** Buttons, cards, forms and interactive states lack a shared visual language.

## Copy-paste prompt

Act as a UI component/design-system reviewer.

**Website, screenshots or code:** [INSERT]

Inventory only components you can inspect: buttons/links, cards, navigation, forms, badges, icons, modals, menus, headings, borders, corner radii, shadows and hover/focus/disabled/error states.

Separate intentional variants from unnecessary inconsistency. For each recurring component give observed variants, locations, a recommended standard, allowed exceptions, and verification requirements. Propose a **lightweight component specification** that reuses existing styles and tokens, not a new design-system project.

Highlight interactive-state and keyboard-focus risks. Do not imply screenshot review verifies hidden states. If source access is limited, name missing evidence.

Avoid a new component library, UI framework, dependencies or unrelated refactoring. **Stop before changes.**

## Working rules
- Inspect actual available materials; distinguish proven issues from possible ones.
- Preserve functionality, brand, content meaning, framework, and working integrations absent explicit approval.
- Do not invent measurements, verification results, or conformance claims.
